## Feature sprint — checklist administration and HAER (2026-10-30)

Implemented locally: Admin/Manager draft checklist authoring and editing, section and grade/Ex applicability, Pass/Fail/NA, required fail remarks, measurement units/limits, preview, draft revision concurrency, submit/technical approval, immutable publication, clone-to-next-version and archive. Existing templates migrate to Draft, and legacy section/response scale fields stay null until explicitly classified; legacy content does not become approved or acquire guessed technical meaning by default. Published checklist selection is resolved against equipment Ex type and activity grade; activity snapshots retain source/version/protection metadata. HAER metadata fields and explicit Unknown versus confirmed Not Applicable state are available, with Manager/Admin edits; scoped JSON/CSV/PDF/Excel-compatible exports include area filters, per-equipment activity history and outstanding defect statuses. The Excel output is SpreadsheetML `.xls`, not OOXML `.xlsx`.

Validation: API Debug build, API Release build to an isolated output folder, focused synthetic checklist/report tests, HTTP PDF/Excel export tests, full backend regression runner and frontend Jest (23 suites/83 tests) passed. The PDF layout exception found in the initial run was corrected and both synthetic and HTTP PDF export tests pass. EF reports no pending model changes after migration scaffolding. `CHECKLIST_HAER_MIGRATION_REVIEW.sql` is generated for review; it has no table/column drops and replaces the unique snapshot index to include protection type. No SQL migration was applied; persisted SQL validation, live browser operation, client report-header approval and authoritative IEC checklist content remain unverified. `tsc --noEmit` remains red due to existing repository-wide errors, including DOM globals, backup-folder imports and older navigation/mobile typing. The changed checklist/HAER files have no diagnostics in the filtered TypeScript check. No example answers or technical criteria were approved or invented. Tenant enforcement remains disabled.

## First safe package after Phase 0

The earlier Manager bootstrap defect is complete: the intended `BootstrapManager:Password` key is used; Manager configuration is validated independently; and configured active/approved Manager accounts are provisioned with hashed passwords. In-memory checks passed for partial configuration, normalization, hashed credentials, idempotency and role conflict.

The Phase 1 runtime upgrade uses .NET SDK 10.0.401, target `net10.0`, EF Core/SQL Server/InMemory 10.0.13, JwtBearer 10.0.13, and aligned IdentityModel JWT packages 8.19.2. Official NuGet package pages confirm these versions and the .NET 10 target/dependency floor. Official-source restore and API Release build passed. The online vulnerability command could not reach NuGet because the configured local proxy refused the connection. SQL Server script generation passed; the isolated LocalDB-style test harness could not establish a local SQL Server session (SSPI name failure, then loopback access denied), so no test DB was created and actual migration/concurrency execution is unverified.

Tracked settings no longer contain SMTP username/password, JWT signing key or Development bootstrap credentials. The current provider values remain unrotated until the owner completes `CREDENTIAL_ROTATION_CHECKLIST.md`; no live provider account was accessed. Local `appsettings.Production.json` remains ignored and was not read or rewritten. Generated copies were removed from API/test build and publish folders; the project excludes it from build/publish output, and .NET 10 Release output was verified. GitHub workflows were reviewed and YAML-parsed: they run automated security/regression checks and do not invoke SQL verification/repair modes. The workflow's default runner does not execute `--verify-sql` or `--repair-sole-reporting-link`. First GitHub Actions execution remains outstanding; Gitleaks v3 can require the repository owner's license secret, and dependency review may require GitHub Advanced Security on private organization repositories.

## Phase 2 readiness

Phase 2C still has reusable fail-closed ownership resolution, validated request context, tenant-filtered query roots, synthetic cross-tenant checks and the route matrix (now 108 classified actions after the additive activity API). The LocalDB test instance applied migrations and passed persisted activity and backup/restore checks, but uses shared-memory/NTLM (`ENCRYPTED=FALSE`); this is not a TLS certificate rehearsal. ## Dependencies that block larger increments

Tenant and offline/RFID architecture must wait on the decisions in `OPEN_DECISIONS.md`. These are not safe to guess because they change identity ownership, schema, hardware interfaces, security boundaries and acceptance responsibility.

The WhatsApp archives, sample checklist and current signed BRD were not present. The MODEC training report and public SafeEx documents provide useful examples but do not approve rules. Core activity APIs and screens now run in the isolated LocalDB development profile; physical photo upload and Android/device behavior still need verification. Do not create a live SAP connector or universal condition/grade rules; preserve the current SurveySession and QC API contract through the additive compatibility path.

## Feature gap closure without SQL dependency (2026-10-31)

Implemented a manager/Admin campaign workload and agenda view over existing work-package/task and inspector API data. It shows per-inspector open, overdue, inaccessible and completed task counts plus a scheduled agenda with package, area, equipment, grade, inspector, due date and status. The projection is client-side and read-only; it does not alter task status or count QC approval/compliance. Focused synthetic tests cover due/overdue grouping, incomplete/unassigned tasks and date ordering. Validation: full Jest 27 suites/102 tests passed; `npx tsc --noEmit` passed; webpack production build passed. React test renderer emitted existing missing-key warnings in planning/report components. No database migration or SQL connection was used.

Latest user-facing gaps identified from code: missing offline project-document delivery; recurrence definitions do not materialize duplicate-safe tasks; permit/isolation entries are text only and have no readiness/clearance enforcement; archived reports/handover remain Draft without formal approval; tag stock inventory and coverage are absent. These need business decisions (permit authority, recurrence policy, final approval role/state) or external sources (documents, RFID hardware) before completion. Existing inspection, defect, QC and client closure screens/APIs are present but not live-accepted in this task. No synthetic result is evidence of KAS3 reconciliation, persisted SQL behavior, Android durability or operational acceptance. Tenant enforcement remains disabled and nothing was deployed.

## Feature sprint — offline reference documents (2026-11-02)

Project plans are designated required when present; area images are optional. Manifest entries include stable identity/revision, file name/type, size, SHA-256 and scope. The download action requires an active approved Surveyor assigned to the task and verifies project/area scope server-side. Versioned document-use records can be stored with offline activities, but `InspectionActivities:DocumentUsageEnabled` defaults to false until migration `20261102044951_OfflineInspectionDocumentUsage` is applied and validated; that migration is additive and generated for review only.

Clear account cache does not run as part of session expiry, so pending inspections/documents remain. The decrypted viewer copy is private app cache, deleted on close and cleaned on application process start.

Validation: frontend Jest 27 suites/107 tests, TypeScript check, webpack production build, API Release build, EF no-pending-model-change check, and focused synthetic EF InMemory offline API checks pass. No SQL database was contacted or modified. Android build/device behavior, true local encryption/storage recovery and SQL persistence remain unverified. Document administration for equipment certificates, custom document categories, expiration/supersession approval and other client file types still requires schema/UI work and business decisions. No production access/deployment; tenant enforcement remains off.
