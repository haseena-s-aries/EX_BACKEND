## Evidence classification

- **Confirmed from repository:** modern equipment is `AreaEquipment`; each modern equipment pin has at most one `SurveySession` due to the unique filtered EF index. Checklist answers are unique per session/question and hold only string value/comment. One `QcReview` per session is enforced. These facts were verified in `SurveyModels.cs` and `SurveyDbContext.OnModelCreating`.
- **Confirmed public-site descriptions:** SafeEx's current product page lists planning/scheduling, sequential inspection tasks, inspection grade/proof of presence, RFID/QR, offline operation, activity/evidence, work-order management, asset history, dashboards, reports/filtered exports, conditions/prioritization, and SAP/Maximo API integration. These are vendor statements about the product. They do not establish a particular account's configuration, exact screen behavior, customer deployment, offline conflict semantics or a contractual obligation.
- **Confirmed public product-document object vocabulary:** the 2024 SafeEx Cloud and Integrability PDF depicts an object model including Equipment/Equipment Group, Plan/Plan Task (regular and corrective items), Checklist/Category/Check, Activity, Response, Response Condition and Response Correction. The glossary describes Activity as checklist output on equipment and Response as the outcome of a check. This is a useful comparison structure; it does not prescribe Ex-Survey table names, Aries scales or KAS3 roles.
- **Confirmed from supplied task:** user expects repeated activity history, checkpoint-level applicability/results/evidence/review, corrective-action history, specified SAP/Ex metadata, and per-equipment/campaign reports.
- **Confirmed from the supplied MODEC report:** item `SWE-50528` has Close and Visual activities, an activity-level acceptance, per-check condition/state, and a documented correction with SAP work-order narrative and photos. This single training example does not define universal condition/grade codes, a contract workflow, or required KAS3 closure authority.
- **Suggested design, pending approval:** immutable activity revisions and versioned question snapshots; a separate technical condition dimension from workflow status; event-based corrective-action decisions; neutral per-equipment and campaign report models. These are architectural recommendations, not claims about SafeEx screens or approved Aries requirements.
- **Not confirmed:** exact SafeEx labels, sequence, role permissions, button behavior, fields, modes, color semantics, signatures, screenshot/page workflow, report layout, any MODEC condition codes and any client SAP identifiers. Do not reproduce proprietary branding or interface design.

## Phase 2D implementation status

The new activity/task/checkpoint/finding/corrective-action entities and isolated model/policy checks are implemented locally as an additive foundation. This changes implementation evidence only; it does not turn SafeEx behaviors into Aries requirements or mark the associated Aries FR/NFR IDs complete. See `SAFEEX_REQUIREMENT_ACCEPTANCE_MATRIX.md`, `PHASE2D_INSPECTION_FOUNDATION.md` and `PHASE2D_TEST_RESULTS.md` for model scope and limitations. No route/report/UI uses these records yet, and the EF model snapshot still requires approved tooling regeneration and isolated SQL rehearsal.

## Proposed non-invasive implementation sequence

1. Review and approve the activity/checkpoint/action model in `INSPECTION_ACTIVITY_DATA_MODEL.md`.
2. Agree terminology, condition and grade authorities, immutable version behavior, review roles, client closure, data retention and compatibility rules.
3. Implement additive persistence behind feature flags; first migration remains non-production and must be rehearsed on an isolated database. Do not alter the existing single-session index until a reviewed compatibility migration maps existing sessions to activities.
4. Add model/policy tests and report fixtures; retain existing `SurveySession`, QC, auth and role APIs until client workflow acceptance.
5. Add SAP metadata fields only after approved field mapping; no live connector in this package.
